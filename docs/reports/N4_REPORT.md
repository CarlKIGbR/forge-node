## M-112 — flaky `test_concurrent_overlapping_batches_store_each_record_once`
**Root cause (concurrency):** the test started 8 threads with batches `recs[:25]`, `recs[10:]`, `recs[:40]`, `recs[20:35]` (×2). `ingest_audit` serialises per chain with `pg_advisory_xact_lock`, but *which* thread gets the lock first is the scheduler's choice. When a batch that starts at seq 11 or 21 wins it while the head is 0, the hub correctly reports `audit_gap: priv-gap-1` and **quarantines the node** — the final `not quarantine` assertion fails (reproduced: reply `{'ok': False, 'rejected': {'seq': 11, 'reason': 'priv-gap-1'}}`, `quarantine_reason 'audit_gap: priv-gap-1'`). The product is right (a batch beyond head+1 *is* a gap); the test's precondition depended on lock order. **Fix (test only):** seed seq 1–5, use batches starting at seq 1/6 (valid whatever the order, still overlapping differently), release all threads with a barrier, assert all 8 deliveries `ok`, exactly 35 records stored in total (each by one delivery), 40 rows, no quarantine, chains verify. Base (e4b9efa, test unchanged): 5 blocks × up to 50 consecutive runs — `FN_REPEAT: run 46 FAILED`, `run 49 FAILED`, 3 blocks 50/50 passed (plus a failure on run 1 of an earlier series): flake rate ≈ 1–2 %, 1 in 6 in one short series. **Branch, fixed test: 50 of 50 consecutive runs passed** (`FN_REPEAT=50 scripts/run-tests.sh -q <test id>`; also repeated on the final tree, see below).
